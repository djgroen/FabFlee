# Running an external model on a supercomputer with FabFlee (multi-node QCG-PilotJob)

Status: **working note / draft** (not committed). Describes how an external,
weather-coupled single-scale Flee model was brought into FabFlee and executed
on ARCHER2 across several nodes with QCG-PilotJob.

See also the generic FabSim3 mechanics in the
[QCG-PilotJob documentation](https://fabsim3.readthedocs.io/en/latest/qcg_pilot/)
(especially *Multi-node execution and resource tuning*).

## 1. Context

The task was to run a model that lives in its **own** repository — the
weather-coupled single-scale Flee model ("DFlee", `alirezajahani60/DFlee`, tag
`v-dflee-scirep-2026` = commit `030ba3d`) — through FabSim3/FabFlee on a
supercomputer, producing both:

- a **core ensemble** (4 counterfactuals M0–M3 × 5 seeds = 20 runs), and
- a **threshold sweep** (`q1 × q2 × Q × seed` = 3 × 3 × 3 × 5 = 135 runs).

Nothing in the FabSim3 core was modified; all integration lives in the FabFlee
plugin.

## 2. Model, patch and runner

| Piece | Where | Notes |
|-------|-------|-------|
| Model source (`flee_src`) | `$flee_location` (e.g. `/work/<proj>/<proj>/<user>/flee_src`) | Pinned to tag `030ba3d`. |
| Weather patch | model's `flee/weather_coupling.py` | Applied by `templates/flee_weather`. |
| Runner | `run_par.py` from the model's `flee_patch/` | **Use this one.** The tag's own `runscripts/run_par.py` crashes with a `ZeroDivisionError` in `displaced_from_origin_pct`. |

`templates/flee_weather` installs the patch **atomically and idempotently**
(write to a temp file, then `mv`; guarded by `grep -qs "def configure"`), so it
is safe when many runs start concurrently from the same `flee_src`.

## 3. Self-contained configuration

All model data and settings live under
`plugins/FabFlee/config_files/ssudan2016_weather/`, so a run needs **only this
config** (no external `handoff/` directory):

```
config_files/ssudan2016_weather/
├── input_csv/           # model inputs (incl. locations.csv)
├── source_data/         # conflict/weather inputs
├── simsetting.yml       # sweep settings: awareness_level=3, hasten=1, logs OFF
├── simsetting_core.yml  # core settings: same + agent/link logs ON
└── SWEEP/<label>/wc_args  # generated by the task (per-run flags)
```

- `simsetting_core.yml` enables agent/link logging (the paper's core setup);
  `simsetting.yml` keeps logging off to save disk during the sweep.
- `flee_weather_ensemble` chooses the file automatically by `mode`
  (`core` → `simsetting_core.yml`, `sweep` → `simsetting.yml`), or you can pass
  `simsetting=<file>`.

## 4. Running

```bash
# Core ensemble (1 node, 20 runs)
fabsim archer2 "flee_weather_ensemble:ssudan2016_weather,mode=core,pj_type=qcg,venv=true,label=v3core,cores=128,cpuspertask=2,taskspernode=64,job_wall_time=0-06:00:00"

# Threshold sweep (3 nodes, 135 runs, single wave)
fabsim archer2 "flee_weather_ensemble:ssudan2016_weather,mode=sweep,pj_type=qcg,venv=true,label=v3sweep,cores=384,cpuspertask=1,taskspernode=64,job_wall_time=0-12:00:00"
```

`pj_type=qcg` selects the QCG-PilotJob backend; the task blanks the machine's
`run_command` for pilot backends so `srun` is not nested inside each task.

## 5. Machine configuration (ARCHER2)

`fabsim/deploy/machines_user.yml`:

```yaml
archer2:
  username: <your-username>     # your ARCHER2 username
  budget: <your-budget>         # your project budget code
  project: <your-project>       # your project code
  flee_location: /work/$project/$project/$username/flee_src
  job_wall_time: '0-12:00:00'
  partition_name: "standard"
  qos_name: "standard"
  cores: 128            # total cores requested -> nodes = cores / 128
  corespernode: 128     # ARCHER2: 128 cores/node
  cpuspertask: 2
  taskspernode: 64
  virtual_env_path: /work/$project/$project/$username/VirtualEnv
```

## 6. Multi-node execution

FabSim computes `nodes = ceil(cores / corespernode)`; requesting `cores=384`
therefore asks SLURM for 3 nodes. QCG-PilotJob then detects the whole SLURM
allocation automatically and starts one agent per node via `srun -w <node>`
(confirm with the per-node `QCG/nl-agent-<node>.log` files).

Concurrency is `nodes × taskspernode ÷ cpuspertask`. For the 135-run sweep we
used **3 nodes × 64 tasks/node ÷ 1 = 192 concurrent tasks**, i.e. a single wave,
with 64 processes per node (memory-safe). Full mechanics are in the
[FabSim3 QCG-PilotJob docs](https://fabsim3.readthedocs.io/en/latest/qcg_pilot/).

## 7. Validation

Summarise the core agent logs with the model's analysis script (run from its
virtual environment):

```bash
python3 scripts/analyze_logs.py <RUNS_dir> \
        --locations <model>/input_csv/locations.csv --procs 20
```

This writes `summary/` into each run and a `logs_summary_runs.csv`. Mean ARD
over seeds for the core ensemble:

| Counterfactual | Mean ARD |
|----------------|----------|
| M0 | 0.8047 |
| M1 | 0.7991 |
| M2 | 0.8048 |
| M3 | 0.7987 |

These match the target values (≈0.81 / ≈0.80). An earlier mismatch was traced to
`awareness_level: 1` (should be `3`) and `hasten: 100` (should be `1`) in an
older settings file.

## 8. Operational notes

- **`out.csv` is written at run-end** (buffered), so mid-run line counts stay at
  the header — don't use them to track progress; read the run's `run.log`
  (`Time = <day>`) instead.
- **Wall time:** a single run took ≈4.5 h here. Set `job_wall_time` explicitly.
- **Disk:** core runs with agent logging produce ≈145 GB of `agents.out.*`; keep
  the raw logs on the machine and ship only summaries.
- **Archive-transfer gotchas:** `rsync --delete-excluded` can crash
  (`buffer overflow: recv_rules`) — use plain `rsync -az`. `ripgrep` is not
  installed on the ARCHER2 login node — use `grep`.
- **SSH sessions:** long-running logins drop; run long waits as background jobs
  on the login node (`nohup setsid …`) and poll the resulting status/marker
  files.

## 9. Packaging results for sharing

```bash
tar czf results_to_return.tgz \
    --exclude='agents.out.*' --exclude='links.out.*' runs runs_sweep
```

Keep the raw logs on the machine until the summaries have been checked.
